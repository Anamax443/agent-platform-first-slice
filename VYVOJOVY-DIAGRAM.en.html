How one document passes through a system that must not trust it

Two views. First, the path of every single command through the security chain: what is checked, in which order, and where it can end. Second, the run of a whole flow from an e-mail to a notification with every ending that is allowed to happen.

1 · The path of one command

every step of every flow

Classification, stamp or e-mail: every command passes the same gate. None of it is done by the component itself; the router and the executor host are platform, and the component receives the command only after the last "yes".

  1. 1

    The caller never says who it is. The gateway takes the identity from authentication (an identity table in tests, Cloudflare Access on the farm), builds a TrustedContext with tenant and scopes and signs { message, context }. The payload cannot claim anything trusted about itself. Tests SEC-CTX-003, SEC-CRED-002..003.

  2. 2

    The router checks in a fixed order and the first failure ends it: envelope shape, accepted binding mechanism, signature against the key valid at signing time, context expiry, caller scope, capability version, platform policy grant for the tenant, capability input schema. The AI identity holds a single scope, so it hits the wall at the fifth check for any write. Tests SEC-PRIV-001, CTR-TIME-001.

  3. 3

    A read-only handler gets data only. The classifier and the validator hold no credential and cannot write; their output passes an output schema and an enum allowlist. An injection in the text has nowhere to overflow. Tests SEC-INJ-001..002.

  4. 4

    The executor host repeats the check right before the write: host allowlist, tenant of the targeted resource against the context, deadline with 30 s clock tolerance, idempotency key (a seen key returns the original outcome and writes nothing), audit before and after. Each of these guards has a mutant that switches it off and a test that notices. Tests SEC-CTX-002, IDM-REPLAY-001, IDM-DEADLINE-001..002, mutants MUT-*.

  5. 5

    An unknown outcome is a state, not an error. When the external system answers unclearly, the host returns UNKNOWN_OUTCOME with a reference and never repeats the write on its own; what happens next is the orchestrator's job (diagram 2, step 4).

2 · The run of a flow from e-mail to notification

mail-intake.v1 · document-intake.v1 = steps 2–4

The orchestrator holds a workflow as a closed list of steps and states. Every diamond is a decision by code, not by the model. On the right are all the endings that may happen: there is no other.

  1. 1

    Many inputs, one duty. E-mail and API exist; GUI, Telegram and Slack are planned. Every channel is its own small component with the same duty: identity from the channel (never from the content), the original under a hash, start the workflow. The router and the later steps never see the channel; they get an artifact and a trusted context. Ingest stores, it does not interpret. The whole mail is one immutable original with a hash; sender address and subject are stored as untrusted data. A full store is an explicit, retryable failure, never a silent acceptance. Tests EVD-001, RES-STOR-001.

  2. 2

    The model proposes, code approves. An answer outside the allowed set is not a security error but a quality one: the orchestrator tries another strategy (rules) under a new key. An instruction hidden in the text causes at most a second attempt. Tests SEC-INJ-001, IDM-STRAT-001.

  3. 3

    Second signal and registry. The validator recomputes the document type by rules over the text with instruction-like lines removed; disagreement goes to a human. The registry answer is untrusted until it passes the range and semantic checks. Tests INT-FAIL-001..004, scenario disputed-classification.

  4. 4

    The stamp is a derivation. The original is never overwritten. When the DMS does not answer clearly, the host returns an unknown outcome, the orchestrator asks three times by client reference and only then calls the operator. Meanwhile the published state is "unclear, being resolved", never a premature "done" or "failed". Tests WF-UNK-001..003, RES-CRASH-001.

  5. 5

    Mail leaves from its own credential domain. The mail executor is a separate host with a single permission: send. The recipient is never named by the payload or the mail, only by a key into the allowlist in platform policy. The irreversible action carries a business identity at the provider, so even a lost answer never produces a second e-mail. Tests SEC-HOST-001, IDM-RET-002, SEC-CTX-002 between flows.

  6. 6

    Three endings and no fourth. Success, waiting for a human with a deadline and escalation, or an explicit failure with a code. A reviewer decides only with a verified role, tenant and binding to the specific task. Tests WF-REV-003..004, EVD-003.

  7. 7

    At the end there is no hub, there are executors. Every output channel is its own write executor with the same discipline: target only from an allowlist, one idempotency key = one side effect, deadline, reconciliation of an unknown outcome, audit before and after. Stamp, e-mail and review exist; a Slack or Telegram message is the same component as e-mail with another adapter; accounting, DMS and payment are HIGH, so an own deployable, human approval and semantic validators per SEC-SEM-001. Journal and audit accompany every ending, not only success.
